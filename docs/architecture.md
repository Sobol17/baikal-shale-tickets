# Архитектура

Shale Tickets строится как модульный монолит на Laravel 13. Приложение остается одним деплоем и одной кодовой базой, но доменная логика разделяется по модулям.

## Архитектурный стиль

Модульный монолит выбран как баланс между скоростью разработки и контролем сложности. Каждый модуль отвечает за свой домен и содержит связанные модели, HTTP-слой, action-классы и DTO/data-классы. Общий код выносится в `Shared`.

Контроллеры остаются тонкими. Основные пользовательские сценарии реализуются в action-классах. Интеграции с внешними сервисами изолируются за контрактами, чтобы доменная логика не зависела от конкретного API.

## Целевые модули

- `Excursions` - экскурсии, описание, сезонные категории, цены и диапазоны доступных дат.
- `Bookings` - гостевые бронирования, данные покупателя, сопровождающие, выбранная дата, статусы, фиксация заказа.
- `Payments` - платежные намерения, callbacks/webhooks, статусы оплаты.
- `Notifications` - email-уведомления после успешной оплаты.
- `Analytics` - агрегированная административная статистика по платежам, бронированиям и экскурсиям.
- `Shared` - общие value objects, исключения, базовые контракты и вспомогательные классы.

## Платежи

Платежная интеграция строится через контракт `PaymentGateway`. Домен бронирования не должен вызывать API Т-Банка напрямую.

Первая реальная реализация контракта - T-Bank gateway. Она отвечает за создание платежа, обработку callback/webhook данных и нормализацию внешних статусов в статусы приложения.

Такой подход позволяет тестировать бронирование через fake gateway и при необходимости добавить другого платежного провайдера без переписывания доменной логики.

## Frontend

Для первой версии используется Blade + Alpine. Это дает server-side rendering внутри Laravel, простую интеграцию с формами и достаточную интерактивность для выбора даты, количества взрослых/детских билетов, заполнения сопровождающих и прохождения бронирования.

Отдельное SPA не входит в архитектурный фокус v1.

## Целевая структура папок

Эта структура описывает направление развития проекта. Папки создаются по мере появления соответствующего кода, а не заранее без необходимости.

```text
app/
  Modules/
    Excursions/
      Models/
      Http/
      Actions/
      Data/
    Bookings/
      Models/
      Http/
      Actions/
      Data/
    Payments/
      Contracts/
      Gateways/
      Http/
      Models/
      Data/
    Notifications/
      Mail/
      Actions/
    Analytics/
      Actions/
      Data/
    Shared/
      Data/
      Exceptions/
      Support/
database/
  migrations/
  seeders/
resources/
  views/
    excursions/
    bookings/
docs/
  project-overview.md
  code-style.md
  architecture.md
```

## Границы v1

В первом архитектурном фокусе не реализуются личный кабинет, аккаунты клиентов, админ-панель и возвраты платежей. Они могут быть добавлены позже как отдельные модули или расширения существующих модулей.
